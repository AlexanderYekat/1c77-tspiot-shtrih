## Цель

При `глИспользоватьВнешнуюПрограммуДляПечатиЧекаИПроверкиМарок = 1` все операции с ККТ выполняются через `proxy-1c-fmuapi` → Delphi `kktserverindy`, а не напрямую через `AddIn.DrvFR`.

Архитектура — **как у разрешительного режима**:

```text
fr_elves-12
    ↓
razresh_regim_check
    ↓
permissive_regime_2024  →  proxy :2579/kkt/...  →  Delphi :2580
```

Проверка марок для РР по-прежнему через `/document` (FMU API).  
Проверка марок на ККТ и печать чека — через `/kkt/...`.

## Этап 1. HTTP-слой ККТ в `permissive_regime_2024`

Все обращения к proxy для ККТ — **только в этом модуле**, рядом с `ОтправитьМаркуНаПроверку` для `/document`.

### 1.1. Базовый транспорт

- [x] `HTTPЗапросКПрокси(Метод, ApiPath, JSONТело, кодОшибки, ОписаниеРезультата)` — универсальный вызов через `глСоединение` / `V7HttpReader`
- [x] `ПроксиАдресККТ(Путь)` → `http://localhost:2579/kkt` + `Путь`
- [x] Подключение компоненты `V7PLUS.DLL` перед запросом (как в РР)
- [x] Кодировка тела запроса UTF-8 (`ПреобразоватьСтрокуВУТФ8`)
- [x] Разбор ответа UTF-8 (`ПреобразоватьСтрокуИзУТФ8`)
- [x] Успех: HTTP 200 и `result = 1` в JSON

### 1.2. Обёртки по endpoint'ам

| Функция | HTTP | Чек-поинт |
|---------|------|-----------|
| `ПолучитьИнфоККТ()` | GET `/kkt/info` | [x] |
| `ПечатьЧекаККТ(json)` | POST `/kkt/print-check` | [x] |
| `ПроверитьМаркуККТ(json)` | POST `/kkt/check-marks` | [x] |
| `СтатусПроверкиМаркиККТ(taskId)` | GET `/kkt/check-marks/status?taskId=...` | [x] |

| `XОтчетККТ()` | POST `/kkt/x-report` | [x] |

### 1.3. Разбор ответов ККТ

- [x] Расширить разбор JSON для полей: `result`, `description`, `connected`, `inn`, `fnNumber`, `serialNumber`
- [x] `checkNumber`, `documentNumber` — для номера чека / смены
- [x] `allAccepted`, `marks[]`, `taskId`, `status` — для проверки марок

**Критерий завершения этапа 1:** из тестовой кнопки или модального вызова успешно отрабатывают GET `/kkt/info` и POST `/kkt/print-check` с тестовым JSON.

## Этап 4. Сборка JSON чека (`СобратьJSONЧекаДляВнешнейПечати`)

Повторить логику `ПечататьЧек` (строки ~113–374), но выдавать JSON по `ТЗ_print-check_json.md`.

### 4.1. Шапка чека

- [x] `type`: `sell` / `sellReturn` по `ПризнВозврата`
- [x] `taxationType` — захардкожено (например `usnIncome`)
- [x] `operator.name` — захардкожено или из параметра `ИмяКассира` формы
- [x] `payments[]` — маппинг `Оплата`: 0→`cash`, 1→`electronically`, 2→`credit` (сумма `Получено`)
- [x] `total` — `СписокТоваров.Итог("Сумма")`

### 4.2. Позиции (`type: "position"`)

- [x] `name`, `price`, `quantity`, `department`
- [x] `tax.type`: `none` (как сейчас в `ПечататьЧек`)
- [x] `paymentObject`: `commodity`; при марке — сервер выставит 33
- [x] `paymentMethod`: `fullPayment`
- [x] `mark` — base64 от `ПодготовитьМаркуДляККТ(Маркировка)` (формат как в `ПечататьЧек`: GS-разделители)
- [x] `markAccepted: true` — если марка уже принята через `/kkt/check-marks` (колонка `МаркаПринятаККТ`)
- [x] `permission` — при РР и приходе: `uuid` + `time` из `СписокТоваров` после `ЗапусититьПроверкуРазрешительныйРежим`

### 4.3. Нефискальный текст (`type: "text"`)

В том же порядке, что `PrintString` в `ПечататьЧек`:

- [x] После каждой позиции: `ЦЕНА ЗА ЕД`, `СКИДКА (%)`, `СКИДКА (АКЦИЯ (%))`, `СКИДКА СУММА`
- [x] Перед закрытием: пробел + «Оплата по терминалу» при `Оплата = 1`
- [x] `Код продавца` + `НП`
- [x] Итоги скидки, накопления (`ИтогДК`)
- [x] Акционные оговорки при `Константа.Акция > 0`

### 4.4. Вспомогательные функции

- [x] `ПодготовитьМаркуДляККТ(Марка)` — `Сред(…)+Симв(29)+…` → base64
- [x] `КодироватьBase64` — локальная копия (из `permissive_regime_2024`)

**Критерий завершения этапа 4:** JSON, собранный 1С, проходит smoke `python kkt_client_emulator.py print-check --json …` (структура и порядок `items[]`).
